# Native Qwen3-ASR and ANE runtime capability audit

## Scope and evidence

This note answers a narrower question than protocol compliance: which Qwen3-ASR capabilities are present in the released model/toolkit, which are actually implemented by the local ANE inference engine, and which require another model or an algorithm. A declared `supported: false` is correct only when the engine truly cannot provide the requested semantic; it is not evidence that the feature has been adopted.

Inspected revisions are the clean local official Qwen checkout `references/Qwen3-ASR` at `7c6daf77a2421100f5fb066495372c00129d39ff`, the fresh Standard ASR audit checkout at `1b2cf3fa5860c075e5160eb60b26b708a7c8bfea`, and the plugin baseline `884c22e`. No model weights were downloaded or executed. The static findings below were checked against the source paths cited. The existing fake-native tests for streaming, audio-prefix reuse, speculative decoding, transcript draft, and offline audio batching passed: 188 passed in 0.68 seconds. That establishes only control-flow and mock-graph behavior, not Core ML fidelity, placement, recognition quality, or forced-alignment accuracy.

The following distinctions are used throughout:

| Status | Meaning |
| --- | --- |
| Present | The released Qwen API or the ANE runtime implements the semantic now. |
| Engine gap | The model/toolkit has a route, but this plugin does not implement the needed inference/runtime behavior. |
| Extra model/algorithm | A valid feature needs a separate learned model or segmentation/reconciliation algorithm. It cannot be obtained by changing a capability flag. |
| Safely unsupported | The model exposes no operation with the required contract, so advertising the feature would be misleading. |

## What is already real

Qwen3-ASR itself has offline and vLLM streaming wrappers, optional free-text `context`, either automatic language output or one forced language, and greedy EOS termination. The official wrapper accepts a list of audio items and independently broadcasts `context` and `language` per item; it feeds chunks to either the Transformers or vLLM backend (`references/Qwen3-ASR/qwen_asr/inference/qwen3_asr.py:300-446`, `:467-537`). The model code's audio tower intentionally encodes each audio item separately even when a higher-level batch is passed (`references/Qwen3-ASR/qwen_asr/core/transformers_backend/modeling_qwen3_asr.py:1099-1133`).

The local runtime correctly implements the single-utterance path rather than merely forwarding flags:

- It recreates the official system/user prompt shape, inserts context into the empty system slot, appends a forced Qwen language control only when requested, and checks exact prompt-plus-generation cache capacity (`std_qwen3asr_ane/src/std_qwen3asr_ane/runtime.py:210-233`, `:575-628`).
- It maintains private decoder state per streaming session and reuses only byte-for-byte equal prompt embeddings at token-batch boundaries; it does not pretend that changed audio embeddings are reusable (`std_qwen3asr_ane/src/std_qwen3asr_ane/streaming_context.py:30-153`). The audio context likewise reuses only matching 100-frame frontend chunks and 104-token encoder windows (`std_qwen3asr_ane/src/std_qwen3asr_ane/audio_context.py:87-173`).
- It emits revisable cumulative partials with `stable_until=0`, then one `closed` result after tail flushing. There is no fabricated speech clock: `audio_prefix_seconds` is in `extra`, not an ASR timestamp (`std_qwen3asr_ane/src/std_qwen3asr_ane/streaming.py:152-165`, `:198-264`).
- It stops only on either configured EOS token and refuses a max-token completion without EOS, instead of returning a silently truncated transcript (`std_qwen3asr_ane/src/std_qwen3asr_ane/runtime.py:364-370`, `:732-804`; speculative path `std_qwen3asr_ane/src/std_qwen3asr_ane/speculative.py:45-112`). The optional 0.6B GPU draft is verifier-only; every emitted token remains the target model's greedy selection (`std_qwen3asr_ane/src/std_qwen3asr_ane/runtime.py:675-730`).

Those are substantive capabilities. They should remain documented as bounded, cumulative streaming rather than being recast as native causal audio streaming, speaker segmentation, timestamps, or a multi-input batch engine.

## Findings and priorities

### P1 — BCP-47 language refinements are admitted by Standard ASR, then rejected by native prompting

**Classification:** confirmed engine/adaptor defect. **Consequence:** a normal request such as `language="en-US"` is valid as a refinement of the declared `en` control, but batch transcription becomes a wrapped `TranscriptionError` and streaming ends with `invalid_audio_or_context`. Base tags continue to work, so this is not a universal outage.

Standard ASR explicitly accepts a refinement of a declared base language and retains the request tag with a `language_refinement_accepted` diagnostic; its reference test uses `en-US` against a declared `en` (`references/standard-asr-audit-2026-09-22/tests/test_asr_interface.py:789-800`; language-resolution authority `src/standard_asr/contract/language.py:192-215`). The plugin passes `params.language` unchanged to the runtime in both batch and streaming (`std_qwen3asr_ane/src/std_qwen3asr_ane/plugin.py:542-572`; `streaming.py:138-145`). `CoreMLRuntime.prepare_prompt` then accepts only a direct key in `LANGUAGE_NAMES` (`runtime.py:575-598`), whose vocabulary contains base Qwen controls only (`languages.py:8-39`). A lightweight native-free reproduction reached that check and raised `ValueError: Unsupported language: en-US`.

**Recommended owner and fix:** adapter/native boundary. Resolve the admitted BCP-47 tag to Qwen's primary language control before prompt construction (`en-US -> en`, `yue-Hant -> yue`), while leaving the Standard ASR effective request and its diagnostic visible to the application. Apply the same conversion to the configured default and to every batch/stream entry point; do not put a regional tag into Qwen's literal `language {name}<asr_text>` suffix.

**Acceptance:** a fake runtime and a real bundle test each cover `en-US`, a script/region refinement, base `en`, and `auto`; forced batch and streaming calls receive the expected Qwen name, produce no `detected_language` for the forced request, preserve the Standard refinement diagnostic, and never emit `invalid_audio_or_context` for an admitted refinement.

### P1 — The released long-audio toolkit is not an ANE long-form engine

**Classification:** confirmed engine gap; the remaining quality work is an extra algorithm, not a larger capability declaration. **Consequence:** the shipped plugin profiles are a 30-second general bundle and a 12-second short-dictation bundle (`std_qwen3asr_ane/src/std_qwen3asr_ane/profiles.py:16-18`). A request beyond the bundle ceiling fails safely (`runtime.py:591-615`) and a streaming session reports the minimum of configured and manifest limits (`streaming.py:113-125`). There is no supported rollover, VAD boundary selection, overlap decode, duplicate removal, or boundary reconciliation.

Qwen's official *toolkit* supports long input by cutting normalized audio around a low-energy point near a maximum duration, with no gaps or overlap, independently transcribing every chunk, then concatenating the text (`references/Qwen3-ASR/qwen_asr/inference/utils.py:246-332`; `qwen3_asr.py:366-446`). That is not proof that the base model has an indefinitely reusable causal audio state. The official streaming implementation likewise accumulates audio from the utterance start and re-feeds all accumulated audio with a rollback prefix (`qwen3_asr.py:657-829`). The ANE engine faithfully uses the same cumulative-utterance pattern and has no persistent causal encoder state (`std_qwen3asr_ane/src/std_qwen3asr_ane/plugin.py:220-229`; `streaming.py:113-150`).

Research notes describe a 4096-position, 180-second candidate, but it is not an exposed product profile or acquisition recipe. Increasing cache length can only relax an input-capacity check; it neither chooses safe segment boundaries nor proves long-form recognition quality. Do not advertise 180 seconds from `stream_max_audio_seconds=180`: the loaded manifest remains the authoritative effective limit.

**Recommended owner and fix:** native engine plus validation. First expose a separately versioned, validated longer bundle only after exact prompt/KV and quality tests. For input beyond that bundle, implement an explicit long-form coordinator: silence-aware or model-backed segmentation, an overlap policy where necessary, text reconciliation, and an immutable-frontier rule. Each emitted closed segment must have an evidence-backed text boundary; sample count or decoder-token count alone is insufficient.

**Acceptance:** compare continuous audio against a declared batch reference for speech through a boundary, cross-boundary words, silence, repetition, noise, and language switching. Report per-language WER/CER and all deletion/duplication behavior at joins. A 30/12-second boundary, the largest intended bundle limit, and the first rollover must each be exercised. The stream may close only reconciled text. No speech timestamps may be attached unless the aligner feature below has produced them.

### P1 — Timestamp capability requires Qwen's separate forced aligner

**Classification:** extra model/algorithm; current unsupported declaration is correct. **Consequence:** callers cannot receive word or segment timestamps from the ANE plugin, although the Qwen release offers an offline path.

Qwen describes the ASR models as recognition/language-ID models and releases `Qwen3-ForcedAligner-0.6B` separately for word/character timestamp prediction, limited to 11 languages and up to five minutes (`references/Qwen3-ASR/README.md:59-67`, `:80-83`). Its wrapper first receives the recognized text and language, then runs a different model to predict timestamp tokens and converts those to structured units (`qwen_asr/inference/qwen3_forced_aligner.py:395-460`). The primary `transcribe` method rejects `return_time_stamps=True` unless that separate model was loaded (`qwen3_asr.py:300-336`). The ANE conversion/runtime bundles only frontend, encoder, decoder, LM head, embeddings, tokenizer, and mel filters (`std_qwen3asr_ane/src/std_qwen3asr_ane/plugin.py:84-92`); it does not package, convert, or invoke an aligner. Standard result words require measured start/end spans, and missing segment timing remains missing rather than defaulting to zero (`references/standard-asr-audit-2026-09-22/src/standard_asr/contract/results.py:235-279`; `src/standard_asr/runtime/streaming.py:939-945`).

**Recommended owner and fix:** a separate optional forced-aligner artifact/runtime and adapter. Gate it by the released aligner's supported-language set, align the final recognized text against the final source audio only, map its units faithfully into Standard words/segments, and disclose unavailable coverage. Streaming timestamps should remain absent until final alignment; do not infer them from update time, chunk duration, token count, or `audio_prefix_seconds`.

**Acceptance:** on held-out supported-language audio, align the exact final transcript and prove every returned unit has finite, ordered time spans within the source duration. Test CJK character units and space-delimited words separately, 300-second limit behavior, unsupported-language rejection, long-form offsets after real segmentation, and no `words`/time fields when the aligner is unavailable.

### P2 — Candidate-language restriction is not a Qwen control

**Classification:** safely unsupported today. The standard parameter means automatic detection constrained to a supplied shortlist (`references/standard-asr-audit-2026-09-22/src/standard_asr/contract/params.py:127-167`). Qwen's public API accepts either `None` for automatic output or one language control per audio; it validates that one value against `SUPPORTED_LANGUAGES` (`references/Qwen3-ASR/qwen_asr/inference/qwen3_asr.py:300-364`; `inference/utils.py:73-106`). It has no candidate list or language-score API.

The local runtime also has a greedy-only language head: it picks a single vocabulary argmax and discards full token scores (`std_qwen3asr_ane/src/std_qwen3asr_ane/runtime.py:266-307`, `:525-542`). Running one forced decode per candidate and choosing a transcript afterward would not implement constrained automatic detection without a defined, calibrated score; it could silently choose the wrong language based on text length or an incomparable greedy path.

**Recommended owner and fix:** retain the unsupported declaration. If the product needs this feature, evaluate a separately validated language-ID front end or a target likelihood/scoring path, then define how it interacts with code-switched audio and context. It is not correct to map candidates to a prompt or to report them as a hard restriction.

**Acceptance before advertisement:** each candidate list demonstrably changes only the language-selection domain, has a documented score/decision rule, rejects or handles a code-switched sample explicitly, and reports the selected language in standard BCP-47 form. Until then, a supplied list must be rejected or diagnosed by Standard ASR, never silently treated as enforced.

### P2 — Compound language metadata is lost

**Classification:** confirmed metadata-loss defect; it matters immediately to API honesty and becomes a larger defect with long-form chunking. Qwen's helper merges languages from independently recognized chunks into a comma-separated source string such as `Chinese,English` (`references/Qwen3-ASR/qwen_asr/inference/utils.py:473-497`). The local parser maps only an exact name to BCP-47 and returns `None` for a compound string (`std_qwen3asr_ane/src/std_qwen3asr_ane/runtime.py:250-263`; the behavior is locked by `tests/test_plugin.py:414-419`). Because the unknown raw value has already been replaced with `None`, the adapter's intended unmapped-language diagnostic cannot disclose it (`plugin.py:624-645`; `streaming.py:167-172`).

This audit found no released-model claim that it identifies every intra-utterance code switch or emits a segment language label. Treat the official merged string as toolkit metadata across independently decoded chunks, not proof of a word-level code-switch feature. The no-speech convention is not affected: official `language None<asr_text>` with no text and the local parser both yield empty text with no detected language (`references/Qwen3-ASR/qwen_asr/inference/utils.py:403-470`; `runtime.py:250-263`). Forced-language streaming also does not duplicate metadata: both implementations append the forced control before a text-only continuation and retain only the generated text as the rollback prefix (`qwen3_asr.py:454-465`, `:748-761`; `runtime.py:210-233`, `:732-787`).

**Recommended owner and fix:** runtime/parser plus adapter. Preserve the raw declared Qwen language before BCP-47 mapping. Emit one standard `detected_language` only when it is a valid single BCP-47 tag; otherwise retain a clearly named engine-specific raw-language field/diagnostic. A future segmenter may expose a measured ordered language sequence, but must not convert a comma string into false segment or word labels.

**Acceptance:** parser tests cover known single languages, `language None`, an absent tag, and `Chinese,English`; the compound result is visibly disclosed but never placed in `detected_language`. Add a long-form two-language-chunk test once segmentation exists and verify ordering, not fabricated per-word attribution.

### P3 — Context is present; hotwords and phrase hints are only an explicit prompt degradation

**Classification:** context present; native phrase-hint boosting safely unsupported. Qwen exposes arbitrary `context` as system-message content (`references/Qwen3-ASR/qwen_asr/inference/qwen3_asr.py:448-465`) and the ANE prompt assembly matches this shape (`runtime.py:210-233`). That is meaningful conditioning, subject to the exact KV budget check. Neither the official Qwen API nor the local model graphs expose a vocabulary-bias, hotword, or phrase-hint decoder input. Passing terms in a free-text context can be useful but provides no hard boost guarantee.

**Recommended owner and fix:** keep `prompt` supported. Allow Standard ASR's already explicit `phrase_hints -> prompt` degradation only when the caller opts in and receives its diagnostic; do not mark phrase hints natively supported. Any future native hotword claim needs a model-supported score/bias mechanism plus measured gains and regressions.

**Acceptance:** exact prompt-template/token tests for context and forced language, exact rejection on cache overflow, and an opt-in phrase-hint degradation test that shows the terms and diagnostic. No acceptance criterion should assert that an arbitrary term must be recognized unless a new trained/scored mechanism exists.

### P3 — Multi-input batching has not reached the ANE inference scheduler

**Classification:** engine gap. The Qwen wrapper handles independent audio/context/language lists and chunks execution at `max_inference_batch_size` (`qwen3_asr.py:338-383`, `:490-537`). The current plugin receives one `PreparedAudio` per `_transcribe` call, shares one inference lock, and serializes calls (`std_qwen3asr_ane/src/std_qwen3asr_ane/plugin.py:542-579`; `runtime.py:310-315`). Its optional B4 front-end graph is an offline optimization for several 100-frame chunks *within one clip*, falling back to B1 for an incomplete group; it is explicitly not an input-clip scheduler (`std_qwen3asr_ane/src/std_qwen3asr_ane/audio_batch.py:9-48`; `bundle.py:9-26`). The streaming path correctly uses session-owned B1/reuse state instead of waiting for a batch.

Standard ASR's `batch` capability is offline whole-input recognition, not a promise that one API call accepts a list of recordings. Therefore this is not a false protocol declaration, but it is a missing throughput feature compared with Qwen's toolkit.

**Recommended owner and fix:** native runtime/scheduler outside streaming. Add a bounded queue that groups independent offline requests only when their audio and prompt shapes fit exported graphs; preserve per-item language/context, request order, cancellation, artifact errors, and the existing serialized Core ML state rules. Do not batch live streams merely to fill a queue.

**Acceptance:** compare B1 and grouped result token IDs/text for heterogeneous duration, language, context, a short tail group, EOS at different positions, and one failed item. Demonstrate no cross-request KV or prompt reuse, original result ordering, bounded latency under low load, and a measured throughput benefit on a real Core ML bundle.

### Addendum — P2: cancellation ends output promptly but does not stop the current cumulative inference

**Classification:** confirmed native scheduling gap; current terminal-output behavior is correct. **Consequence:** cancellation frees a blocked audio producer and delivers the terminal `cancelled` event without waiting, but an already-started worker can continue feature extraction, encoder calls, decoder prefill, and every remaining generation call for that cumulative utterance while holding the one shared engine lock. A later batch request or streaming session consequently waits for all of that work, not merely the one Core ML prediction that was active when cancellation arrived.

`Qwen3ASRSession.cancel()` sets an asyncio event and a thread-safe event. `_until_cancelled()` then races the `asyncio.to_thread()` wrapper against that event, raises `_Cancelled`, and cancels the wrapper (`std_qwen3asr_ane/src/std_qwen3asr_ane/streaming.py:86-111`). This correctly prevents `_decode()` from committing a late result, so no partial or closed event can follow the cancellation. It cannot stop the Python worker thread. That worker checks `_native_cancelled` once before calling `runtime.transcribe`, then holds `_inference_lock` until the whole call returns (`streaming.py:113-150`). The existing cancellation test deliberately unblocks its fake runtime only *after* the consumer has received `cancelled` (`std_qwen3asr_ane/tests/test_streaming.py:203-231`), so it verifies prompt output/input release rather than prompt engine-lock release.

The statement that a Core ML prediction cannot be hard-preempted remains true. It should not be read to mean that the whole cumulative transcription is indivisible: the runtime makes many separate synchronous predictions. Audio-prefix encoding has one prediction per changed frontend chunk and encoder window (`audio_context.py:112-172`); decoder prefill calls every decoder partition for each token block (`streaming_context.py:98-153`; `runtime.py:481-523`); generation alternates an LM-head prediction and a decoder step (`runtime.py:759-776`). The speculative batch path has further independent draft, target, and verify-head calls (`runtime.py:675-730`; `speculative.py:70-111`; `runtime.py:863-900`).

**Recommended owner and fix:** native runtime plus streaming adapter. Thread an optional cancellation probe owned by the session into runtime transcription. Check it immediately before and after each native prediction boundary, then raise one dedicated cancellation exception. The session worker should reset its decoder and audio contexts and translate that exception to its existing terminal cancellation path. The current reset rules make this safe: an interrupted audio encode clears its cache (`audio_context.py:87-110`), and a failed decoder prefill requires fresh states (`streaming_context.py:68-76`, `:125-153`). Keep the engine lock until the active native prediction has returned and cleanup has completed; never reset state concurrently from the event-loop thread.

The hook must also cover speculative decoding if a cancellable batch API is later added. Its target cursor owns fresh target states, but `MLXDraft` holds a mutable cache; cancellation needs an explicit draft-cache invalidation before another request may use it (`draft.py:123-178`). Checking only between outer speculative blocks is insufficient because proposal, target verification, and verify-head work are separate calls. Existing batch APIs have no cancellation contract, so this is a future-proof runtime hook rather than a reason to invent one.

**Acceptance:** use a blocking fake prediction to cancel after the first, middle, and final frontend/encoder/decoder/head boundary. In every case, after the one active call is released, a second request acquires the engine lock without waiting for the abandoned utterance's remaining planned calls; the cancelled session emits one terminal `cancelled`, no subsequent content, and retains no result. Retry the same streaming context and compare it with a fresh inference to prove no stale audio or KV state was reused. For speculative coverage, inject cancellation during draft prepare, proposal, verifier decode, and verify-head selection; the next decode must match a fresh serial target result. A real Core ML run should report the number of predictions after cancellation and establish the honest bound: one active native prediction plus bounded CPU cleanup, never a claim of mid-prediction preemption.

## Coverage, limits, and recommended sequence

Inspected native code: `plugin.py`, `runtime.py`, `streaming.py`, `audio.py`, `audio_batch.py`, `audio_context.py`, `streaming_context.py`, `languages.py`, `draft.py`, `speculative.py`, `transcript_draft.py`, `bundle.py`, `profiles.py`, and conversion `build.py`, `encoder.py`, `decoder.py`, `draft.py`, and `embedding.py`. Inspected official code: the README, inference wrapper, streaming implementation, audio utilities, forced aligner, processor, Transformers audio model, and vLLM entry points. Inspected Standard ASR's fresh capabilities, parameters, language resolution, results, engine and streaming reducer authority paths.

Unverified boundaries are real model accuracy, all 30 language controls and dialect recognition, code-switch behavior, Core ML numerical parity/ANE placement, a compiled 4096-position bundle, forced-aligner conversion feasibility, real batched throughput, and long-form join quality. None should be inferred from the mock test pass.

Recommended implementation order is: fix BCP-47 refinement mapping; preserve/disclose non-single language metadata; add isolated cooperative-cancellation hooks that do not alter transcript semantics; decide whether a validated long-form coordinator is a product goal; then add optional forced alignment and only afterward consider language shortlist and input batching. This order fixes a currently admitted request, prevents metadata loss and avoidable lock occupation, and keeps all future timing/language claims evidence-based.
